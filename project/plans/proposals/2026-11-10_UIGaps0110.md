# Design Proposal: closing the gaps the dashboard hit on 0.10.0 (0.11.0)

**Status:** approved by the brief of 2026-11-10 (owner), implemented on `feature/ui-gaps-0.11.0` from 0.10.0 (`f8a2f7a`).
**Evidence (read only):** the dashboard's port branch, final commit `08a87a2`: `project/summaries/2026-11-10_design-tokens-adoption.md`,
`project/checklists/CURRENT_design-tokens.md`, and the code that stayed hand-rolled (`EqualHeightGrid`, the Stack Map gap card,
`Role.color`, `FlowLayout`, the status sheet helpers, `ProjectDetailView`'s segmented fallback); iPhone and iPad simulator runs and Mac
crops from the owner's review. **Visual spec:** the owner-approved "Swiss and Apple" artifact (square chips, borderless gap cards with the
3 pt top rule, section headings clearly above row labels and values).
**Breaking:** yes, source-breaking where stated in section 6. No shims.

## 1. Objective

The dashboard ported onto 0.10.0 and still hand-rolled seven things. Each is a function of the tokens, so each belongs in
`DesignTokensSwiftUI`. Where an item needs a number from the design, the number is a token (theme structure, text roles, palette), not a literal in a
component; `SwissSourceDisciplineTests` keeps scanning every source file.

## 2. Decisions, gap by gap (built / built differently / declined, with the evidence)

| # | Gap | Verdict | API shape |
|---|-----|---------|-----------|
| 1 | Type hierarchy: section headings have no prominence on a Mac | **Built** | `UIRole.section`, `UIRole.cardTitle`; per-platform text styles; `UITextSpec.pointSize` and a tested ordering |
| 2 | Borderless, equal-height card with a pinned footer; equal-height grid | **Built** | `.swissCardChrome(_:)`, `SwissEqualGrid`, `SwissEqualGridLayout`, wrapping `SwissCardFooter` |
| 3 | Table: empty cells shift columns, selection, copy, tree rows, sort path, phone widths | **Built** | `SwissTable(selection:children:expanded:)`, `SwissTableColumn(sortBy:copy:)`, `SwissTableSorting`, `SwissTableCopy`, `SwissTableTree`, stacked layout |
| 4 | A SwiftUI `Color` from an `Adaptive` | **Built** | `Adaptive.dynamicColor` (and `AppPalette.dynamicColor(_:)`) |
| 5 | Square chips; caution and warning | **Built** | `OutlinedChip(shape:)` defaults to the container radius; `StatusKind.caution`, `ChipTone.caution` |
| 6 | Segmented control breaks words at accessibility sizes | **Built** | automatic menu fallback, `SwissSegmentedPresentation`, one-line segments, 44 pt targets |
| 7 | Public wrap layout | **Built** | `SwissFlowLayout`, `SwissFlowArrangement` |

Out of scope, as briefed: form-control styles (declined in 0.10.0), SwiftCLIKit and SwiftGUIKit.

### 2.1 Type (gap 1)

**Evidence.** Measured on the macOS 27.2 SDK with `NSFont.preferredFont(forTextStyle:)`: largeTitle 26, title 22, title2 17, title3 15,
headline 13, body 13, callout 12, subheadline 11, footnote 10, caption 10, caption2 10. iOS (default size) is 34 / 28 / 22 / 20 / 17 / 17 / 16 / 15 /
13 / 12 / 11. `heading` maps to `.headline`, 13 pt on a Mac: the same size as the value next to it (only the weight differs). The card
title is `.title`, 22 pt, which is larger than any heading a section can have.

**Decision.** Two new roles and a platform-aware mapping.

| Role | macOS style (pt) | iPhone style (pt) | Reads theme role |
|---|---|---|---|
| `display` | largeTitle (26) | largeTitle (34) | `display` |
| `title` | title (22) | title (28) | `uiTitle` |
| `section` (new) | title2 (17) | title3 (20) | `heading` (700) |
| `cardTitle` (new) | title3 (15) | headline (17) | `uiTitle` (800), as the card has always been |
| `heading` | headline (13) | headline (17) | `heading` |
| `body` | body (13) | body (17) | `body` |
| `caption` | footnote (10) | footnote (13) | `caption` |
| `label` | caption2 (10) | caption2 (11) | `label` |

A single text style cannot serve both: 17 to 20 pt on a Mac is `title2`, but on a phone `title2` is 22 and the owner's phone hierarchy
(28 / 20 / 17 / 17) needs `title3`. The mapping is therefore by platform (`#if os(macOS)`), which is what Dynamic Type itself does (the
styles are not the same size on a Mac), and the ordering is a property the tests state.

**No new core `TypeStyle`/`TypeRole`.** The tokens' sizes are web pixels (heading 28, title 34) and the UI register ignores them in
favour of Dynamic Type; a new `section` token would add a web size nobody asked for (the web already has `heading` 28 as the section
heading of the approved design: its h2) and would change `tokens.css`. Weight, design, capitals and tracking stay the theme's: `section`
reads the theme's `heading` (700), `cardTitle` the `uiTitle` (800). A theme that changes either changes the role.

**Test.** `UITextSpec.pointSize` resolves the text style on the platform (`NSFont` or `UIFont`, default size) so that a test measures
and does not recite. The property asserted on macOS (`swift test`) and on iOS (`xcodebuild test` on a simulator) is
`display > title > section > cardTitle >= heading >= body > caption >= label`. Strictness is only where both platforms have it: a phone's heading and body are both 17
(they differ in weight), a Mac's caption and label are both 10, and a phone's caption (13) is above its label (11). On macOS the test also asserts the owner's numbers (section 17 to 20, label and caption 10, body 13).

### 2.2 Card and equal-height grid (gap 2)

The card gets a chrome environment (`.swissCardChrome(.borderless)`; the 3 pt top rule stays, since it is the card's identity). A card that
is offered a taller height than it needs pins its footer to the bottom edge: a flexible spacer sits above the footer's hairline. The card
only claims height when it sits in a `SwissEqualGrid` (an environment flag the grid sets), so a card in a plain `VStack` does not
grab leftover space. `SwissEqualGrid` is a `View` over a public `SwissEqualGridLayout` (equal-width columns, as many as fit at
`minimumColumnWidth`, each row as tall as its tallest child, a lone last child keeps the column width). The arithmetic is public
(`SwissEqualGridArrangement`) so a test holds it. `SwissCardFooter` wraps (`SwissFlowLayout`) and takes views, so buttons stay buttons.

### 2.3 Table (gap 3)

* **Empty cells.** A cell's content that draws nothing is zero subviews, and the row layout places subviews by index, so every column
  after it moved left. Each cell is now wrapped in a view that always exists; a test measures the cell origins under a probe.
* **Selection.** `SwissTable(rows, columns:, selection: Binding<Row.ID?>)` (single) and `selection: Binding<Set<Row.ID>>` (multiple).
  Tap selects (Mac: command or shift toggles; touch: tap toggles in multiple mode); up and down arrows move; the row says
  `.isSelected`. A selected row is the `rule` colour as a fill with a 3 pt accent bar: no tint.
* **Copy.** Cmd-C and a context menu "Copy" put the selected rows on the pasteboard as tab-separated text, in table order
  (`SwissTableCopy.text`, pure). A column supplies `copy:` or, for a text column, its text.
* **Tree rows.** `SwissTable(rows, children: \.children, ...)`, `expanded: Binding<Set<Row.ID>>?` (internal state when nil). The first column
  is indented by depth and a chevron (44 pt target on touch) toggles; the row is `.accessibilityExpanded`. `SwissTableTree.flatten` is pure.
* **Sort path.** `SwissTableColumn(..., sortBy: \.count)` (any `Comparable`) or `compare:`; when a column has one, the table sorts its
  rows by the binding it already has (`SwissTableSorting.sorted`, stable, per sibling level in a tree). A column without one only reports.
* **Narrow.** Below `minimumWidth` (default `SwissMetrics.tableStackedBelow`, 600 pt) or at an accessibility text size the rows stack: the
  first column is the row's title, the others are label / value pairs under it. `narrow: .scroll` keeps 0.10.0's horizontal scroll.

### 2.4 Colour (gap 4)

`Adaptive.dynamicColor` returns a `Color` backed by `NSColor(name:dynamicProvider:)` / `UIColor(dynamicProvider:)`, which resolves light,
dark and the increased-contrast variants when drawn, with no environment read. A test resolves it under light and dark and compares it with
`Adaptive.value(in:increasedContrast:)`. Measured on macOS 27.2: `NSAppearance(named: .accessibilityHighContrastAqua)` reports itself as plain Aqua, so on a Mac Increase Contrast reaches the
provider only as `NSWorkspace.accessibilityDisplayShouldIncreaseContrast`; the slot choice is a pure function tested with that flag, and UIKit (iOS) tests resolve the high-contrast traits directly.

### 2.5 Chips and status (gap 5)

`OutlinedChip` takes `shape: ChipShape = .container` (the theme's container radius: square in Swiss, as in the approved design) or `.control`.
`StatusKind` and `ChipTone` gain `.caution`. The package's existing `warning` role is a yellow-brown that the core documents as
"Caution", and the dashboard's palette has that yellow as `caution` and an orange as `warning`. So: `.caution` is the existing role (renamed
at the kind level), and `.warning` becomes the stronger orange, read from `palette.extras["alert"]`, which Swiss now declares
(light #B04A00, dark #FF7A3D, increased #8F3B00 and #FF9A70; the dark is redder than the system orange because #FF9F0A was 3 from the accent and 7.7 from the caution yellow in OKLab). Themes with no `alert` fall back to their `warning`. Tests: every tone's outline measures at least 3:1 (WCAG
1.4.11) on the background and the card surface in light, dark and both increased-contrast variants, and caution and warning stay apart.

### 2.6 Segmented control (gap 6)

One line per segment (`lineLimit(1)`, no hyphenation). `SwissSegmentedPresentation.resolve(typeSize:fits:)` is pure: segments when the type size is not
an accessibility size and the segments fit the width, otherwise a menu (`Menu` with a styled label, 44 pt on touch). `ViewThatFits`
supplies "fits". `presentation: .automatic | .segments | .menu`.

### 2.7 Flow (gap 7)

`SwissFlowLayout(spacing:lineSpacing:)`, a `Layout`; `SwissFlowArrangement.rows` is pure.

## 3. Non-goals

Form-control styles; SwiftCLIKit, SwiftGUIKit; a new core `TypeStyle`; dragging or reordering rows; column resizing; a data model for the table.

## 4. Test plan (written first)

Unit tests per measurable property: the type ordering and the Mac numbers; platform size resolution; `Adaptive.dynamicColor` under each appearance;
chip tone contrast; `StatusKind` mapping; equal-grid columns, widths and row heights; flow rows; table: cell origins with empty cells, flatten,
sort, copy text, selection updates, stacking decision; segmented presentation; source discipline. Gallery scenes rendered light and dark,
looked at. iOS: the type ordering test and the dynamic-colour test run on an iOS Simulator with `xcodebuild test`.

## 5. Build matrix to attempt

macOS `swift build` and `swift test`; `xcodebuild` for the iOS Simulator and visionOS Simulator for `DesignTokensSwiftUI` (and `test` on iOS); the core is
Foundation-only (a test); no Linux toolchain is available here.

## 6. Source-breaking changes

* `StatusKind.warning` is now the orange; the yellow is `StatusKind.caution` (and `ChipTone` likewise). `StatusKind.role` became `StatusKind.adaptive(in:)`.
* `OutlinedChip` is square by default (container radius); pass `shape: .control` for 0.10.0's.
* `SwissCard` titles are `cardTitle`, smaller on a Mac (22 to 15).
* `SwissTable`: `minimumWidth` now stacks below the width instead of scrolling (`narrow: .scroll` restores it); the table sorts rows itself when a column has `sortBy`.
* `SwissCardFooter(_:names:)` is unchanged; it now wraps.
